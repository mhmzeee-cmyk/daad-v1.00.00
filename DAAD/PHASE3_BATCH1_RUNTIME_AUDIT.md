# PHASE 3 — Batch 1: Runtime Architecture Audit

## 1. Executive Summary

The DAAD compiler has NO separate runtime library. The compiler generates self-contained x86-64 assembly with direct syscalls for process exit. This minimalist approach works correctly for the tested programs.

## 2. Runtime Architecture

### Architecture Type

**Self-contained assembly with direct syscalls**

The compiler generates:
- `_start` entry point (not `main`)
- Direct `syscall` for process exit (syscall 60)
- No runtime functions needed for basic programs

### Execution Pipeline

```
.daad source
    ↓
Lexer (lexer.c)
    ↓
Parser (parser.c)
    ↓
Semantic (semantic_visitor.c)
    ↓
IR Builder (ir_builder.c)
    ↓
Optimizer (optimizer_pass.c)
    ↓
Backend (backend_interface.c)
    ↓
x86-64 Assembly (.s file)
    ↓
gcc/as (assembler + linker)
    ↓
Executable (.exe)
    ↓
OS execution
```

## 3. Runtime Files

**No separate runtime files exist.**

The compiler generates all runtime support inline:
```asm
.global _start
_start:
  callq main
  movq %rax, %rdi    # exit code
  movq $60, %rax     # syscall number (exit)
  syscall
```

## 4. Runtime API Inventory

**No runtime APIs exist.**

The compiler uses direct syscalls for process exit.

## 5. Compiler → Runtime Integration

### Integration Point

The compiler generates `_start` entry point in `main.c:117-122`:

```c
fprintf(out, "\n.global _start\n");
fprintf(out, "_start:\n");
fprintf(out, "  callq main\n");
fprintf(out, "  movq %%rax, %%rdi\n");
fprintf(out, "  movq $60, %%rax\n");
fprintf(out, "  syscall\n");
```

### Symbol Resolution

- `main` is generated by the backend for the `الرئيسية()` function
- `_start` is the OS entry point
- `syscall` is handled by the kernel
